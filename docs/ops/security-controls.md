# สรุปมาตรการความปลอดภัยและการควบคุมการเปลี่ยนแปลง (QMS Portal)

เอกสารนี้สรุปมาตรการที่ระบบมีอยู่ในตัวโค้ด พร้อมที่ตรวจสอบหลักฐาน ข้อจำกัดที่ทราบอยู่ในหัวข้อสุดท้ายโดยตั้งใจ เพื่อให้ผู้ตรวจเห็นภาพจริง
สถานะ ณ วันที่ 2026-10-21 (ระบบขึ้นใช้งานจริงบน Cloudflare แล้ว มีผู้ใช้เฉพาะผู้ดูแลระบบ ยังไม่ได้นำเข้ารายชื่อพนักงาน)

## 1. มาตรการในระบบ

| หัวข้อ | มาตรการ | วิธีตรวจหลักฐาน |
|---|---|---|
| การยืนยันตัวตน | ล็อกอินด้วยอีเมลและรหัสผ่าน เก็บรหัสผ่านแบบ PBKDF2-SHA256 พร้อม salt สุ่มรายคน ไม่เก็บรหัสผ่านจริง | โค้ด `apps/api/src/password.js` |
| การยืนยันตัวตนสองขั้นตอน (2FA) | แอป Authenticator (TOTP) บังคับตามนโยบายที่ DCC ตั้งเองในหน้าข้อมูลหลัก (ตั้งต้น: DCC ทุกคนและระดับ L5 ขึ้นไป) ผู้ที่ถูกบังคับต้องตั้งค่าก่อนใช้งานอื่น มีรหัสสำรองใช้ครั้งเดียว 8 ชุด (เก็บเฉพาะค่าแฮช) รหัสผิดนับรวมกับการล็อกบัญชี รหัสเดียวใช้ซ้ำไม่ได้ DCC รีเซ็ตให้ผู้ที่โทรศัพท์หายได้ (บันทึกใน Audit log) | เทสต์ `two_factor.test.js`, `totp.test.js` (ตรงตามค่าตัวอย่าง RFC 6238) |
| นโยบายรหัสผ่าน | ยาว 12–128 ตัวอักษร ผู้ใช้ที่ DCC สร้างให้ต้องเปลี่ยนรหัสผ่านเองก่อนใช้งานครั้งแรก เปลี่ยนรหัสแล้ว Token เดิมทุกอันใช้ไม่ได้ | เทสต์ `security.test.js` |
| กันการเดารหัสผ่าน | ผิด 5 ครั้งล็อกบัญชี (ต้องให้ DCC ปลดล็อก) และจำกัดการล็อกอินผิดต่อ IP (10 ครั้งใน 15 นาที) ข้อความเมื่อผิดไม่บอกว่าอีเมลมีหรือไม่ | เทสต์ `auth.test.js`, `security.test.js` |
| Session | Token อายุ 8 ชั่วโมง ทุกคำขอตรวจสถานะผู้ใช้จากฐานข้อมูลใหม่ การล็อกบัญชีหรือลดสิทธิ์มีผลทันที | `requireAuth` ใน `apps/api/src/index.js` |
| สิทธิ์การเข้าถึง | เซิร์ฟเวอร์ตรวจสิทธิ์ทุกคำขอ: ระดับผู้ขอ/ผู้ทบทวน/ผู้อนุมัติตาม Approval Matrix, การแยกหน้าที่ (ผู้ขอ ผู้ทบทวน ผู้อนุมัติเป็นคนละคน), เอกสารเฉพาะแผนกเห็นได้เฉพาะแผนกนั้น, DCC และ QMR | เทสต์ `approval.test.js`, `dars.test.js`, `documents.test.js` |
| Audit trail | บันทึกการล็อกอิน (สำเร็จ/ล้มเหลว+IP), การเปิดดูและดาวน์โหลดไฟล์เอกสาร (ใคร เอกสารไหน ฉบับไหน ดูหรือดาวน์โหลด), การแก้นโยบายความปลอดภัย, การยื่น ทบทวน อนุมัติ ปฏิเสธ ประกาศใช้ ยกเลิกเอกสาร, การแก้ Approval Matrix, การปลดล็อกบัญชี, การเปลี่ยนรหัสผ่าน, การดาวน์โหลด Audit log บันทึกในธุรกรรมเดียวกับการกระทำ (ถ้าบันทึกไม่ได้ การกระทำนั้นไม่เกิด) | ตาราง `audit_log` |

## 2. สิ่งที่องค์กรต้องทำเอง (นอกโค้ด)

- เปิด Two-factor (2FA) ให้บัญชี Cloudflare, GitHub และ Google ของผู้ดูแลระบบทุกคน (ผู้ดูแลระบบคนปัจจุบันเปิดครบแล้วเมื่อ 2026-10-21 คนที่เพิ่มภายหลังต้องเปิดก่อนได้สิทธิ์)
- จำกัดคนที่มีสิทธิ์ในบัญชี Cloudflare/GitHub และทบทวนรายชื่อปีละครั้ง
- กำหนดผู้รับผิดชอบสำรอง (อย่างน้อย 2 คน) ที่รู้รหัสเข้ารหัส backup
- ทบทวนรายชื่อผู้ใช้และระดับสิทธิ์ในระบบปีละครั้ง (ดาวน์โหลดรายชื่อได้จากฐานข้อมูล หรือขอ DCC)

## 3. ข้อจำกัดที่ทราบ

- ไม่มี SSO กับ Microsoft 365 ในระบบนี้ (2FA ใช้แอป Authenticator ของระบบเอง) และความลับของ 2FA เก็บในฐานข้อมูลแบบอ่านกลับได้ (จำเป็นต่อการคำนวณรหัส) ปลอดภัยเท่ากับตัวฐานข้อมูลและไฟล์สำรองที่เข้ารหัส
- ถ้า DCC เป็นคนเดียวและเสียทั้งโทรศัพท์และรหัสสำรอง ไม่มีใครรีเซ็ตให้ได้ ต้องให้ผู้ดูแลเทคนิคแก้ที่ฐานข้อมูล จึงควรมี DCC สำรองอย่างน้อย 1 คน
- รหัสผ่านใช้ PBKDF2 100,000 รอบ ซึ่งเป็นเพดานของ Cloudflare Workers ต่ำกว่าคำแนะนำล่าสุดของ OWASP แต่ชดเชยด้วยการจำกัดความถี่และการล็อกบัญชี
- ระบบบันทึกการเปิดดูบนจอและการดาวน์โหลด แต่แยกไม่ได้ว่าไฟล์ที่ดาวน์โหลดไปถูกพิมพ์หรือส่งต่อหรือไม่
- ผู้ที่รู้อีเมลของผู้ใช้สามารถทำให้บัญชีนั้นถูกล็อกได้ด้วยการพิมพ์รหัสผิด DCC ปลดล็อกได้ ควรเพิ่มกฎ Rate Limiting ของ Cloudflare อีกชั้นเมื่อ deploy
- ช่องโหว่ของแพ็กเกจ `xlsx` (ยังไม่มีเวอร์ชันแก้) ไม่กระทบ เพราะใช้สร้างไฟล์ส่งออกเท่านั้น ไม่อ่านไฟล์ที่ผู้ใช้อัปโหลด
- ยังไม่มีการทดสอบเจาะระบบ (penetration test) โดยผู้เชี่ยวชาญอิสระ และยังไม่ได้ประเมินเทียบมาตรฐานเฉพาะ เช่น ISO 27001 หรือ PDPA
- ระบบสำรองข้อมูลรันจริงสำเร็จแล้ว แต่มีเงื่อนไขที่ต้องแก้ก่อนใช้ระยะยาว (ดู `docs/ops/backup-restore.md` หัวข้อ 7)
