# กรณีทดสอบ UAT: ระบบกลาง (Portal Core) และ DCC

ใช้คู่กับ `docs/uat/vcc/` (VCC) และ `docs/uat/periodic-review/` (ทบทวนตามรอบ) เอกสารนี้ครอบคลุมส่วนที่ยังไม่มีกรณีทดสอบแบบ markdown:
การเข้าสู่ระบบ ความปลอดภัยของ session สิทธิ์ Audit log และวงจรเอกสาร DCC

## กติกาการทดสอบ

- ทดสอบบนสภาพแวดล้อม **UAT** เท่านั้น ห้ามใช้ข้อมูลจริงของบริษัท ข้อมูลที่สร้างต้องขึ้นต้นด้วย `[ข้อมูลทดสอบ]`
- บัญชีผู้ทดสอบ **DCC สร้างผ่านหน้าจัดการผู้ใช้** (ไม่ใช่ seed) ระบบจะให้รหัสผ่านชั่วคราวครั้งเดียว ห้ามเขียนรหัสผ่านลงในเอกสารนี้หรือ defect log
- เกณฑ์อ้างอิงยึดค่าตั้งค่าปัจจุบัน (Approval Matrix, นโยบาย 2FA, SLA) ที่ DCC ยืนยันก่อนเริ่ม และบันทึกค่าไว้ในหัวข้อ "ค่าตั้งค่าที่ใช้ทดสอบ"
- เมื่อระบบแสดงข้อผิดพลาดที่มี **รหัสอ้างอิง** ให้คัดลอกรหัสนั้นลง defect log ทุกครั้ง
- หลักฐาน: ภาพหน้าจอ + รหัสเอกสาร/รหัสคำขอ + เวลาโดยประมาณ (ให้ผู้ดูแลค้นใน Audit log ได้)

### CORE-UAT-001: เข้าสู่ระบบ ล็อกบัญชี และปลดล็อก
- **ผู้ทดสอบ:** P-REQ, P-DCC
- **ขั้นตอน:**
  1. P-REQ เข้าสู่ระบบด้วยอีเมลและรหัสผ่านที่ถูกต้อง
  2. ออกจากระบบ แล้วกรอกรหัสผ่านผิด 1 ครั้ง ด้วยอีเมลที่มีอยู่ และอีกครั้งด้วยอีเมลที่ไม่มีในระบบ
  3. กรอกรหัสผิดต่อเนื่องจนครบ 5 ครั้ง แล้วลองกรอกรหัสที่ถูก
  4. P-DCC เข้าหน้าจัดการผู้ใช้ เปิดรายการบัญชีที่ถูกล็อก แล้วปลดล็อก P-REQ
  5. P-REQ เข้าสู่ระบบด้วยรหัสที่ถูกต้องอีกครั้ง
- **ผลที่คาดหวัง:**
  - ข้อ 2: ข้อความเหมือนกันทั้งสองกรณี "อีเมลหรือรหัสผ่านไม่ถูกต้อง" (ไม่บอกว่าอีเมลมีอยู่หรือไม่)
  - ข้อ 3: บัญชีถูกล็อก ข้อความ "บัญชีถูกล็อก กรุณาติดต่อ DCC"
  - ข้อ 4-5: ปลดล็อกได้ เข้าระบบได้ Audit log มี `LOGIN_FAILED`, `USER_UNLOCKED`, `LOGIN`

### CORE-UAT-002: รหัสผ่านชั่วคราวและบังคับเปลี่ยนรหัส
- **ผู้ทดสอบ:** P-DCC, ผู้ใช้ใหม่
- **ขั้นตอน:**
  1. P-DCC สร้างผู้ใช้ใหม่ จดรหัสชั่วคราวที่ระบบแสดง (แสดงครั้งเดียว) ส่งให้ผู้ใช้โดยตรง
  2. ผู้ใช้ใหม่เข้าสู่ระบบ ระบบต้องให้เปลี่ยนรหัสก่อนทำอย่างอื่น
  3. ลองตั้งรหัสใหม่สั้นกว่า 12 ตัว และลองใช้รหัสเดิมซ้ำ
  4. ตั้งรหัสใหม่ที่ถูกต้อง
  5. P-DCC กด "รีเซ็ตรหัสผ่าน" ให้ผู้ใช้คนเดิมขณะที่ผู้ใช้เปิดหน้าจออยู่ แล้วให้ผู้ใช้กดเมนูใดก็ได้
- **ผลที่คาดหวัง:** ข้อ 3 ถูกปฏิเสธพร้อมเหตุผล; ข้อ 4 ใช้งานต่อได้; ข้อ 5 ผู้ใช้หลุดออกจากระบบทันทีและต้องใช้รหัสชั่วคราวใหม่ Audit log มี `USER_CREATED`, `PASSWORD_CHANGED`, `USER_PASSWORD_RESET`

### CORE-UAT-003: การยืนยันตัวตนสองขั้นตอน (2FA)
- **ผู้ทดสอบ:** P-DCC (หรือผู้ใช้ที่นโยบายบังคับ)
- **ขั้นตอน:**
  1. เข้าสู่ระบบครั้งแรก ระบบให้ตั้งค่า 2FA ก่อนใช้งาน สแกน QR ด้วยแอป Authenticator แล้วยืนยันรหัส
  2. เก็บรหัสสำรอง 8 ชุดไว้ในที่ปลอดภัย
  3. ออกจากระบบ เข้าใหม่ กรอกรหัสผิด 1 ครั้ง แล้วกรอกรหัสที่ถูก
  4. ออกจากระบบ เข้าใหม่โดยใช้รหัสสำรอง 1 ชุด แล้วลองใช้รหัสสำรองชุดเดิมซ้ำในการเข้ารอบถัดไป
  5. (ถ้านโยบายเปิดจำอุปกรณ์) ติ๊ก "จดจำอุปกรณ์นี้" แล้วเข้าใหม่ ต้องไม่ถามรหัส; ทดสอบบนเครื่องส่วนตัวเท่านั้น
- **ผลที่คาดหวัง:** ข้อ 3 รหัสผิดถูกปฏิเสธและนับรวมกับการล็อกบัญชี; ข้อ 4 รหัสสำรองใช้ได้ครั้งเดียว; Audit log มี `TWO_FACTOR_ENABLED`, `LOGIN` (ระบุวิธี)

### CORE-UAT-004: ความปลอดภัยของ session บนเครื่องใช้ร่วม
- **ผู้ทดสอบ:** P-REQ แล้วตามด้วย P-OTH บนเครื่องเดียวกัน (เบราว์เซอร์เดียวกัน)
- **ขั้นตอน:**
  1. P-REQ เข้าสู่ระบบ เปิดทะเบียนเอกสารและรายการ DAR ของตน
  2. เริ่มกรอกคำขอ DAR ใหม่แต่ **ไม่ส่ง** (เป็นฉบับร่าง)
  3. **ปิดแท็บโดยไม่กดออกจากระบบ** แล้วเปิดเว็บใหม่
  4. ผู้ดูแลเปิด DevTools (F12) → Application → Local Storage → `qms-api-mode-storage` ตรวจเนื้อหา
  5. P-OTH เข้าสู่ระบบบนเครื่องเดิม
- **ผลที่คาดหวัง:**
  - ข้อ 3: ระบบให้เข้าสู่ระบบใหม่
  - ข้อ 4: Local Storage มีเฉพาะฉบับร่าง DAR ไม่มีรายชื่อผู้ใช้ อีเมล เอกสาร หรือ Action log
  - ข้อ 5: P-OTH เห็นเฉพาะข้อมูลตามสิทธิ์ของตน
- **ข้อจำกัดที่ทราบ:** ฉบับร่าง DAR ที่ยังไม่ส่งถูกเก็บไว้ในเบราว์เซอร์ตามการออกแบบเดิม (กันงานที่พิมพ์ไว้หาย) ให้บันทึกผลที่เห็นจริงในข้อ 5 ว่าผู้ใช้คนถัดไปเห็นร่างของคนก่อนหรือไม่ เพื่อให้เจ้าของระบบตัดสินใจ
- **ต้องมีโค้ดจาก PR #151** บน UAT ก่อนทดสอบข้อนี้

### CORE-UAT-005: รหัสอ้างอิงข้อผิดพลาด
- **ผู้ทดสอบ:** ผู้ดูแลระบบ (ทดสอบเชิงเทคนิค)
- **ขั้นตอน:**
  1. เปิด DevTools → Network แล้วใช้งานหน้าใดก็ได้ ดู header `X-Request-Id` ของคำขอไปที่ API
  2. ถ้าระหว่าง UAT มีข้อความ "เกิดข้อผิดพลาดในระบบ ... รหัสอ้างอิง ..." ให้ผู้ดูแลค้นรหัสนั้นใน Cloudflare Workers Logs
- **ผลที่คาดหวัง:** ทุกคำขอมี `X-Request-Id`; รหัสในข้อความ error ค้นเจอใน log พร้อมเส้นทางและผู้ใช้ (ไม่มีรหัสผ่านหรือเนื้อหาเอกสารใน log)
- **ต้องมีโค้ดจาก PR #150** บน UAT ก่อนทดสอบข้อนี้

### CORE-UAT-006: สิทธิ์ตามแผนกและเมนู
- **ผู้ทดสอบ:** P-REQ, P-OTH, P-QMR, P-DCC
- **ขั้นตอน:**
  1. P-REQ เปิดทะเบียนเอกสาร ดูเอกสารขอบเขต `DEPT` ของแผนก QA และของแผนกอื่น
  2. P-OTH (PD) ลองเปิดลิงก์เอกสาร `DEPT` ของ QA ที่ P-REQ คัดลอกให้
  3. P-OTH เปิดเมนู VCC และเมนูผู้ดูแลระบบ
  4. P-QMR เปิดเอกสารฉบับที่ถูกแทนที่ (SUPERSEDED) ส่วน P-REQ ลองเปิดฉบับเดียวกัน
- **ผลที่คาดหวัง:** ข้อ 2 แสดง "ไม่พบเอกสาร"; ข้อ 3 PD ไม่เห็นเมนู VCC และเมนูผู้ดูแลระบบ; ข้อ 4 QMR เปิดได้ P-REQ เปิดไฟล์ไม่ได้ ("เอกสารนี้ไม่มีผลบังคับใช้แล้ว")
- **ข้อจำกัดที่ทราบ:** ผู้ใช้ระดับ L6 ขึ้นไปจากแผนกนอก DC/QC/QA/MGT/LB ใช้ VCC ผ่านระบบได้แต่ไม่เห็นเมนู (บันทึกไว้ในรายงานตรวจ F-16) ให้จดผลที่เห็นจริง

### CORE-UAT-007: Audit log และการส่งออกให้ผู้ตรวจ
- **ผู้ทดสอบ:** P-DCC, P-QMR, P-REQ
- **ขั้นตอน:**
  1. P-DCC เปิดหน้า System Action Log กรองตามวันที่วันนี้ และตามโมดูล DCC/VCC
  2. ดาวน์โหลด CSV แล้วเปิดใน Excel
  3. P-REQ ลองเปิดหน้าเดียวกัน
- **ผลที่คาดหวัง:** เห็นรายการที่ทำในกรณีทดสอบก่อนหน้า (ผู้ทำ, เวลา, การกระทำ); CSV อ่านภาษาไทยได้; ค่าที่ขึ้นต้นด้วย `=` ไม่ถูกคำนวณเป็นสูตร; การดาวน์โหลดถูกบันทึกเป็น `AUDIT_LOG_EXPORTED`; P-REQ เข้าไม่ได้

### CORE-UAT-008: การแก้ Approval Matrix และผลต่อการอนุมัติ
- **ผู้ทดสอบ:** P-DCC, P-REQ, P-REV
- **ขั้นตอน:**
  1. P-DCC แก้ Approval Matrix ประเภทเอกสารทดสอบให้ผู้ทบทวนต้องเป็น L5
  2. P-REQ ยื่น DAR ใหม่โดยเลือก P-REV (L4) เป็นผู้ทบทวน
  3. P-DCC คืนค่า Matrix เป็นค่าเดิม
- **ผลที่คาดหวัง:** ข้อ 2 ถูกปฏิเสธพร้อมเหตุผลเรื่องระดับ; Audit log มี `APPROVAL_MATRIX_UPDATED` พร้อมค่าก่อนและหลังทั้งสองครั้ง

### DCC-UAT-001: ขอเอกสารใหม่ (DAR NEW) จนมีผลบังคับใช้
- **ผู้ทดสอบ:** P-REQ, P-REV, P-APP, P-QC4
- **ขั้นตอน:**
  1. P-REQ ยื่น DAR ประเภท NEW (`[ข้อมูลทดสอบ]` ประเภท SOP แผนก QA) ระบุเหตุผล, วันที่มีผล = วันนี้, จุดแจกจ่ายสำเนา 4 จุด (QA 1 จุด แล้วตามด้วย QC 3 จุด), ผู้รับทราบ 1 คน
  2. แนบไฟล์ PDF ทดสอบ แล้วลองแนบไฟล์ที่ไม่ใช่ PDF (เปลี่ยนนามสกุลเป็น .pdf)
  3. P-REV ทบทวนและอนุมัติขั้นทบทวน
  4. P-APP อนุมัติ
  5. เปิดทะเบียนเอกสาร (สถานะมีผลบังคับใช้) และทะเบียนสำเนาควบคุม
- **ผลที่คาดหวัง:** เลข DAR รูปแบบ `DAR-YY-NNN` และรหัสเอกสาร `SOP-QA-NN` ออกโดยระบบ; ไฟล์ปลอมถูกปฏิเสธ "ไฟล์ต้องเป็น PDF"; หลังอนุมัติ เอกสารมีผลทันที (หรือ 00:00 ของวันที่ระบุ ตามเวลาไทย); สำเนา 4 ชุด (หมายเลข 01 ของ QA, 02-04 ของ QC) อยู่สถานะรอออก; ผู้รับทราบมีงานรอรับทราบ; Audit log มี `DAR_SUBMITTED`, `DAR_FILE_ATTACHED`, `DAR_REVIEWED`, `DAR_APPROVED`, `DOCUMENT_PUBLISHED`

### DCC-UAT-002: ส่งกลับแก้ไข ยื่นใหม่ ถอนคำขอ และไม่อนุมัติ
- **ผู้ทดสอบ:** P-REQ, P-REV, P-APP
- **ขั้นตอน:**
  1. P-REQ ยื่น DAR ใหม่อีกฉบับ P-REV กด "ส่งกลับแก้ไข" โดยไม่ใส่เหตุผล แล้วใส่เหตุผล
  2. P-REQ แนบไฟล์ใหม่และยื่นใหม่
  3. P-REV ทบทวนผ่าน P-APP กด "ไม่อนุมัติ" โดยไม่ใส่เหตุผล แล้วใส่เหตุผล
  4. ยื่น DAR ฉบับที่สาม ให้ P-REV ส่งกลับ แล้ว P-REQ "ถอนคำขอ"
- **ผลที่คาดหวัง:** ส่งกลับและไม่อนุมัติบังคับใส่เหตุผล; ยื่นใหม่แล้วเริ่มทบทวนใหม่; ไม่อนุมัติแล้วคำขอปิด; ถอนคำขอแล้วเอกสารว่างให้ยื่นใหม่ได้; Audit log มี `DAR_RETURNED`, `DAR_RESUBMITTED`, `DAR_REJECTED`, `DAR_WITHDRAWN`

### DCC-UAT-003: การแยกหน้าที่ (Separation of Duties)
- **ผู้ทดสอบ:** P-REQ, P-REV, P-DCC
- **ขั้นตอน:**
  1. P-REV ยื่น DAR และเลือกตัวเองเป็นผู้ทบทวน
  2. P-REQ ยื่น DAR โดยเลือก P-REV เป็นทั้งผู้ทบทวนและผู้อนุมัติ
  3. P-REQ ยื่น DAR ของแผนก QA โดยเลือก P-DCC (แผนก DC) เป็นผู้ทบทวน
  4. กดปุ่มอนุมัติสองครั้งเร็ว ๆ (หรือเปิดสองแท็บแล้วกดพร้อมกัน)
- **ผลที่คาดหวัง:** ข้อ 1-3 ถูกปฏิเสธพร้อมเหตุผลภาษาไทย; ข้อ 4 สำเร็จครั้งเดียว อีกครั้งแจ้ง "ถูกพิจารณาไปแล้ว กรุณาโหลดใหม่" และ Audit log มีรายการเดียว

### DCC-UAT-004: แก้ไขเอกสาร (REVISION) และการแยกรายการตามสถานะ
- **ผู้ทดสอบ:** P-REQ, P-REV, P-APP, P-QMR
- **ขั้นตอน:**
  1. P-REQ ยื่น DAR ประเภท REVISION ของเอกสารจาก DCC-UAT-001 ขณะที่มี DAR อื่นค้างอยู่ของเอกสารเดียวกัน (ต้องถูกปฏิเสธ) แล้วยื่นเมื่อไม่มีค้าง
  2. ผ่านการทบทวนและอนุมัติ
  3. เปิดทะเบียนเอกสารแต่ละสถานะ (มีผล / ถูกแทนที่ / ยกเลิก)
- **ผลที่คาดหวัง:** เอกสารหนึ่งมี DAR ค้างได้รายการเดียว; Rev ใหม่มีผล Rev เดิมเป็น SUPERSEDED; รายการแต่ละสถานะไม่ปะปนกัน; สำเนาของ Rev เดิมที่อยู่หน้างานเปลี่ยนเป็นรอเรียกคืน

### DCC-UAT-005: ยกเลิกเอกสาร (OBSOLETE)
- **ผู้ทดสอบ:** P-REQ, P-REV, P-APP
- **ขั้นตอน:** ยื่น DAR ประเภท OBSOLETE ของเอกสารทดสอบ ผ่านการทบทวนและอนุมัติ (ถ้า Matrix ตั้งระดับผู้อนุมัติกรณียกเลิกไว้สูงกว่า ให้ทดสอบว่าผู้อนุมัติระดับปกติถูกปฏิเสธ)
- **ผลที่คาดหวัง:** ไม่ต้องแนบไฟล์; เอกสารย้ายไปรายการ OBSOLETE; ผู้ใช้ทั่วไปเปิดไฟล์ไม่ได้; สำเนาหน้างานรอเรียกคืน; Audit log มี `DOCUMENT_OBSOLETED`

### DCC-UAT-006: วงจรสำเนาควบคุม
- **ผู้ทดสอบ:** P-DCC, P-QC4, P-OTH
- **ขั้นตอน:**
  1. P-DCC แจกจ่ายสำเนาหมายเลข 01-04 จาก DCC-UAT-001
  2. P-OTH ลองยืนยันรับสำเนาของ QC แล้ว P-QC4 ยืนยันรับสำเนา 02-04 (สำเนา 01 ให้หัวหน้า QA ระดับ L4 ยืนยันรับ)
  3. P-QC4 แจ้งสำเนา 02 ชำรุด (ระบุเหตุผล)
  4. P-QC4 ขอย้ายจุดติดตั้งสำเนา 03 แล้ว P-DCC อนุมัติ; ขอส่งคืนสำเนา 04 แล้ว P-DCC ไม่อนุมัติ (ใส่เหตุผล)
  5. ลองขอย้ายหรือส่งคืนสำเนาหมายเลข 01
  6. P-DCC บันทึกเรียกคืนและทำลายสำเนา 02 ที่ชำรุด พร้อมวิธีทำลายและพยาน
- **ผลที่คาดหวัง:** ข้อ 2 P-OTH ถูกปฏิเสธ; ข้อ 3 สำเนาเดิมรอเรียกคืนและมีสำเนาทดแทนเลขครั้งที่ออกถัดไป; ข้อ 5 ถูกปฏิเสธ; ข้อ 6 บันทึกวิธีทำลายและพยานใน Audit log (`CC_DISPOSED`); ทุกขั้นมี Audit log (`CC_DISPATCHED`, `CC_RECEIVED`, `CC_DAMAGED_REPORTED`, `CC_RELOCATION_APPROVED`, `CC_RETURN_REJECTED`)
- **ข้อจำกัดที่ทราบ:** ระดับผู้ยืนยันรับสำเนา (L4) เขียนตายตัวในโค้ด รอ QMR ยืนยัน (Pending QMR Decision ข้อ 3)

### DCC-UAT-007: การรับทราบเอกสาร
- **ผู้ทดสอบ:** ผู้รับทราบที่ระบุใน DCC-UAT-001, P-REQ, P-OTH
- **ขั้นตอน:** ผู้รับทราบเปิดงานรอรับทราบแล้วกดรับทราบ, กดซ้ำ, P-OTH ลองรับทราบแทน
- **ผลที่คาดหวัง:** รับทราบได้ครั้งเดียว; คนอื่นรับทราบแทนไม่ได้; P-REQ เห็นสถานะการรับทราบ; Audit log มี `DOCUMENT_ACKNOWLEDGED`
