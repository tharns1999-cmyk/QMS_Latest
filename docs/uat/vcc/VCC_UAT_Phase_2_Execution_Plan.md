# แผนการเตรียมการและแนวทางปฏิบัติการทดสอบระบบจริง (VCC UAT Phase 2 — Execution Preparation Plan)

เอกสารฉบับนี้กำหนดกรอบการปฏิบัติการ ลำดับการทดสอบ (Execution Sequence), บทบาทหน้าที่ของผู้ทดสอบจริง, การบริหารจัดการหลักฐาน (Evidence Management), กระบวนการคัดกรองข้อบกพร่อง (Defect Triage), และรายการตรวจสอบความปลอดภัยของสภาพแวดล้อมก่อนการเริ่มทดสอบรับมอบระบบ (UAT) ในระยะ Phase 2 ตามมาตรฐาน ISO 9001:2015 และ ISO/IEC 17025:2017

## 3. การเตรียมข้อมูลทดสอบและโครงสร้างแหล่งเก็บหลักฐาน (Test Data & Evidence Repository)

### 3.1 แหล่งเก็บหลักฐานดิจิทัล (Evidence Folders)
หลักฐานทั้งหมดจากการรันการทดสอบ UAT จะถูกจัดเก็บไว้ในโครงสร้างโฟลเดอร์ที่เป็นระบบ:
- **ภาพถ่ายหน้าจอ:** `docs/uat/vcc/evidence/screenshots/`  
  *(ตั้งชื่อ: `VCC-UAT-<ID>_<PERSONA>_<YYYYMMDD>_<STEP>.png`)*
- **เอกสารดาวน์โหลด:** `docs/uat/vcc/evidence/downloads/`  
  *(ไฟล์ PDF ใบรับรองที่ดาวน์โหลดกลับมาตรวจสอบ SHA-256)*
- **ประวัติ Audit Trail:** `docs/uat/vcc/evidence/audit_logs/`  
  *(ไฟล์ส่งออก SQLite Audit Log JSON ยืนยันการบันทึกประวัติ)*

### 3.2 กฎความถูกต้องของหลักฐานดิจิทัล (Evidence Integrity Rules)
1. ภาพถ่ายหน้าจอต้องจับภาพให้เห็น URL, Timestamp ของระบบ และสถานะของหน้าจออย่างชัดเจน
2. ไฟล์ใบรับรองที่ใช้ทดสอบต้องเป็นไฟล์ [`docs/uat/vcc/fixtures/sample_calibration_cert.pdf`](./fixtures/sample_calibration_cert.pdf) ซึ่งระบุว่าเป็นเอกสารจำลองชัดเจน
3. ในขั้นตอน UAT-004 ต้องดาวน์โหลดไฟล์กลับมาและรันคำสั่งตรวจสอบ Hash เพื่อยืนยันว่าตรงกับ `f3b6026cad6f1ddc7d6d096454623a422a8044d268e1a4d5a2dce397f19c1c38`

## 4. กระบวนการคัดกรองข้อบกพร่องและแดชบอร์ดติดตามงาน (Defect Triage & Dashboard)

### 4.1 ขั้นตอนการคัดกรองข้อบกพร่อง (Defect Triage Protocol)
เมื่อผู้ทดสอบตรวจพบพฤติกรรมที่ไม่ตรงตามผลลัพธ์ที่คาดหวัง ให้ดำเนินการตามขั้นตอนดังนี้:
1. **บันทึกลงใน Defect Log ทันที**: ระบุข้อมูลใน [`VCC_UAT_Defect_Log.md`](./VCC_UAT_Defect_Log.md) และ [`VCC_UAT_Defect_Log.csv`](./VCC_UAT_Defect_Log.csv) พร้อมแนบภาพหลักฐาน
2. **จัดระดับความรุนแรงตามเกณฑ์สากล**:
   - **Blocker (ระดับ 1)**: ระบบหยุดทำงาน ข้อมูลเสียหาย หรือระบบความปลอดภัยล้มเหลว -> *หยุดการทดสอบใน Scenario นั้นทันทีและแจ้งทีมพัฒนาแก้ไขด่วน*
   - **Critical (ระดับ 2)**: ฟังก์ชันหลักตามมาตรฐานไม่ทำงาน (เช่น ไม่ออกสถานะ ON_HOLD หรือไม่สร้าง Snapshot) -> *ต้องแก้ไขและทดสอบซ้ำให้ผ่านก่อนจบ Phase 2*
   - **Major (ระดับ 3)**: มีฟังก์ชันติดขัดแต่มีวิธีทำงานทดแทนได้ (Workaround) -> *ประเมินและวางแผนแก้ไข*
   - **Minor (ระดับ 4)**: ข้อผิดพลาดด้านข้อความ UI หรือความสวยงามเล็กน้อย -> *บันทึกปรับปรุงในรอบถัดไป*
3. **การประชุมทบทวนข้อบกพร่องประจำวัน (Daily Defect Review)**:
   - ผู้แทน DCC, QC Manager, และทีมพัฒนา ประชุมสรุปสถานะข้อบกพร่องทุกวันเวลา 16:30 น.
